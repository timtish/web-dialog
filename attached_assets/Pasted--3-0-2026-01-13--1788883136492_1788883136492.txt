Версия: 3.0 (финальная)
Дата: 2026-01-13
Статус: Готово к реализации

1. Контекст и цели

1.1. Проблема
Отец — пенсионер, алкогольная зависимость. Переводит по ~150 ₽ пару раз в день на водку; если не переводить — просит у сестры (ограничение не работает). Срывы приходят с пенсией, просит «на похмелиться».

1.2. Задача-эксперимент
Проверить, получится ли сдвинуть алкоголизм в моменты пенсии — сгладить, уводя общение, давая «мудрые мысли» (harm reduction: «пиво много или водку мало»), делать не скучно. Побочно — заинтересовать ВК-жизнью/общением; отец с ИИ ещё не общался, мессенджер только ВКонтакте.

Признано: это инструмент, который «теоретически может помочь», а не готовое решение проблемы.

1.3. Подача отцу
«Вот есть искусственный интеллект, я пользуюсь по работе, можешь его поспрашивать про алкоголь, может что подскажет». Пусть общается по любому вопросу. НЕ подавать как «опросник/контролёр про алкоголь» с первой фразы — рамка «поговори с собеседником», тема алкоголя всплывает органично.

2. Архитектура (высокоуровнево)

Frontend (одностраничный UI + PWA)
  - HTML/JS/CSS
  - погода (open-meteo) + гороскоп
  |
  | HTTP
  v
Backend (FastAPI, Python)
  - In-memory состояние
  - Персистентность на диск
  |
  +-- Timeweb LLM API (qwen3.7-plus)
  +-- Yandex Search API
  +-- open-meteo (погода)

3. Компоненты системы

3.1. Frontend
- Технологии: HTML + vanilla JS (или Vue/React — на выбор при реализации)
- UI: одностраничный, крупный шрифт, одно поле ввода, без лишних кнопок
- PWA: манифест для установки как приложения из браузера
- Дополнительно: виджет погоды (open-meteo API, бесплатно) + гороскоп (статический текст или простой API)
- Аутентификация: токен/guid в URL (/chat/<guid>), без ввода пароля

3.2. Backend (FastAPI)
- Язык: Python 3.11+
- Фреймворк: FastAPI
- Хостинг: VPS ~1GB RAM
- Задачи:
  * Принимать сообщения от frontend
  * Управлять in-memory состоянием (история + профиль)
  * Персистентность на диск (при запуске вычитывать, при изменениях сбрасывать)
  * Вызывать LLM API (Timeweb)
  * Вызывать Yandex Search API (по запросу модели через tool-calling)
  * Логика сжатия истории по времени

3.3. LLM API
- Провайдер: Timeweb Cloud
- Базовый URL: https://api.timeweb.ai/v1
- Модель: dashscope/qwen3.7-plus
- Формат: OpenAI-совместимый v1
- Стоимость: платная (уточнить тарифы)

3.4. Search API
- Провайдер: Yandex Search API
- Стоимость: платная (уточнить тарифы, квоты)
- Интеграция: через tool-calling модели (проверить надёжность)

3.5. Погода
- Провайдер: open-meteo.com
- Стоимость: бесплатно, без ключа
- Использование: виджет на UI, не требует LLM

4. Хранение данных

4.1. In-memory структура (Python)

class UserSession:
    guid: str                          # уникальный идентификатор (секрет)
    history: list[dict]                # активный диалог [{"role": "user"|"assistant", "content": "..."}]
    profile: str                       # сжатый тематический профиль (Markdown)
    last_response_time: datetime       # время последнего ответа бота
    need_compress: bool                # флаг необходимости сжатия

4.2. Персистентность на диск
- Формат: JSON-файл на пользователя (<guid>.json)
- Содержимое:
  {
    "guid": "...",
    "history": [...],
    "profile": "# Сводный профиль: ...\n\n## Текущее состояние\n...",
    "last_response_time": "2026-01-13T12:34:56",
    "need_compress": false
  }
- Логика:
  * При запуске FastAPI: вычитывать все *.json файлы в директорию sessions/
  * При изменениях (новое сообщение, обновление profile): сбрасывать на диск (debounce ~5 сек, чтобы не писать на каждое сообщение)
  * При shutdown: принудительный сброс

4.3. Сжатый профиль (Markdown)

Формат profile_semantic.md:

# Сводный профиль: [Имя]

## Текущее состояние (Обновлено: [дата])
* Настроение: ...
* Алкоголь: ...
* Общие заметки: ...

## Важные триггеры и риски
* Пенсия: [дата/паттерн]
* Потери: ...
* Конфликты: ...

## Увлечения и темы для увода разговора
* [Увлечение 1]: ...
* [Увлечение 2]: ...

## Социальные связи
* [Человек 1]: ...
* [Человек 2]: ...

5. Логика работы

5.1. Сценарий А: Новый пользователь (первый заход)
1. Frontend открывает /chat/<guid>
2. Backend проверяет: есть ли сессия в памяти/на диске?
   - Если нет: создаёт новую UserSession с пустым history и дефолтным profile
   - Если есть: загружает из памяти/диска
3. Frontend показывает UI, пользователь вводит первое сообщение
4. Backend:
   - Добавляет сообщение в history
   - Формирует запрос к LLM:
     System Prompt: [инструкции по тону, этике, harm reduction]
     + profile (если есть)
     User Message: [первое сообщение]
   - Отправляет в Timeweb API
   - Получает ответ, добавляет в history
   - Обновляет last_response_time
   - Сбрасывает на диск
   - Возвращает ответ frontend

5.2. Сценарий Б: Активный диалог (в пределах короткого времени)
1. Пользователь вводит сообщение
2. Backend:
   - Добавляет сообщение в history
   - Проверяет: прошло ли много времени с last_response_time?
     * Если нет: обычный запрос к LLM с history + profile
     * Если да: сначала сжатие (см. 5.3), потом запрос
   - Отправляет в Timeweb API
   - Получает ответ, добавляет в history
   - Обновляет last_response_time
   - Сбрасывает на диск
   - Возвращает ответ frontend

5.3. Логика сжатия (при следующем запросе после долгого времени)

Триггер: если от last_response_time (например, 30 минут — уточнить при реализации)

Алгоритм:
1. Берём текущий history + старый profile
2. Формируем запрос к LLM (можно использовать ту же модель или дешёвую, если доступна):
   System: "Обнови Markdown-профиль человека на основе свежего диалога. 
   Извлеки новые факты в соответствующие секции (## Увлечения, ## Триггеры, ## Состояние). 
   Если в секции ничего не изменилось, оставь её прежней. Будь очень лаконичен."
   
   User: 
   [старый profile]
   
   ---
   Свежий диалог:
   [history]
3. Получаем обновлённый Markdown
4. Заменяем profile на новый
5. Очищаем history (или оставляем только последнее сообщение как контекст)
6. Сбрасываем на диск
7. Продолжаем обычный сценарий Б

Альтернатива: сжатие не по времени, а по размеру history (например, >20 сообщений) — уточнить при реализации.

5.4. Tool-calling: поиск в интернете

Триггер: модель решает вызвать инструмент «search» (проверить надёжность tool-calling на qwen3.7-plus)

Алгоритм:
1. Модель возвращает tool-call: {"name": "search", "arguments": {"query": "..."}}
2. Backend вызывает Yandex Search API с запросом
3. Получает результаты (snippet + URL)
4. Возвращает результаты модели как tool-response
5. Модель генерирует финальный ответ с учётом поиска

Fallback: если tool-calling ненадёжен, реализовать форсированный поиск на стороне кода (анализ сообщения на вопросительные формулировки → автоматический вызов поиска).

6. API эндпоинты (Backend)

6.1. GET /chat/{guid}
- Возвращает HTML-страницу (frontend)
- Проверяет существование сессии

6.2. POST /api/chat/{guid}
- Request: {"message": "..."}
- Response: {"reply": "...", "search_results": [...]} (опционально)
- Логика: добавление сообщения, сжатие (если нужно), вызов LLM, возврат ответа

6.3. GET /api/profile/{guid}
- Возвращает текущий profile (для отладки/просмотра владельцем)
- Аутентификация: admin-token (отдельный секрет)

6.4. GET /api/history/{guid}
- Возвращает текущий history (для отладки/просмотра владельцем)
- Аутентификация: admin-token

6.5. POST /api/summary/{guid}
- Запрос к LLM: «как настроение, что обсуждали» на основе history + profile
- Аутентификация: admin-token
- Response: {"summary": "..."}

7. Промпт/этика

7.1. System Prompt (базовый)

Ты — дружелюбный собеседник для пожилого человека. Твоя задача — поддерживать разговор, 
интересоваться его жизнью, увлечениями, воспоминаниями. Будь тёплым, внимательным, 
задавай открытые вопросы.

Если разговор заходит про алкоголь:
- НЕ осуждай и НЕ читай нотации («тебе нужно бросить»)
- Используй техники мотивационного интервью: отражение, открытые вопросы
- Мягко предлагай альтернативы (пиво вместо водки, отсрочка), когда тема всплывает сама
- Не форсируй тему алкоголя

Приоритет тем: жизнь, ВК, знакомые, воспоминания, увлечения.

Если пользователь упоминает тяжёлую абстиненцию, суицидальные мысли или острое ухудшение состояния:
- НЕ пытайся «разрулить» сам
- Мягко посоветуй обратиться к сыну или вызвать скорую

Не давай советов «как пить безопаснее» без ограничений.

Будь лаконичен, не используй сложные термины.

7.2. Обновление профиля (промпт для сжатия)

Обнови Markdown-профиль человека на основе свежего диалога. 
Извлеки новые факты в соответствующие секции (## Увлечения, ## Триггеры, ## Состояние). 
Если в секции ничего не изменилось, оставь её прежней. Будь очень лаконичен.

[старый profile]

---
Свежий диалог:
[history]

8. Метрики эксперимента

8.1. Что измеряем
- Частота/сумма переводов на алкоголь по дням (особенно в дни пенсии)
- Частота/длительность разговоров с ботом
- Темы разговоров (через pull-запросы владельца: «как настроение, что обсуждали»)

8.2. Как измеряем
- Логи переводов: вручную (владелец ведёт учёт)
- Логи разговоров: автоматически (backend пишет в sessions/<guid>.log каждое сообщение с timestamp)
- Pull-запросы: эндпоинт /api/summary/{guid}

8.3. Критерий успеха
Субъективный (владелец решает по итогам эксперимента). Гипотеза: если отец начинает чаще открывать чат в дни пенсии и реже просить «на похмелиться» — инструмент работает.

9. Открытые вопросы / решения при реализации

1. Точное значение «много времени» для сжатия: 30 минут? 1 час? Уточнить при реализации.
2. Альтернатива сжатию по времени: сжатие по размеру history (>20 сообщений) — что лучше?
3. Tool-calling на qwen3.7-plus: проверить надёжность. Если падает — реализовать форсированный поиск.
4. Yandex Search API: получить ключ, уточнить тарифы/квоты.
5. Timeweb API: получить ключ, проверить доступность модели dashscope/qwen3.7-plus.
6. Стартовый шаблон profile: создать дефолтный Markdown-шаблон для новых пользователей.
7. Admin-token: сгенерировать секрет для эндпоинтов владельца.
8. Debounced save: настроить debounce ~5 сек для сброса на диск.
